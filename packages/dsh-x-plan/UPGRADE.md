# 升级到 v2 工作流

本次改变的是计划批准、执行门禁、验收与恢复协议；JSON 计划契约版本仍为 `1`。旧计划和历史记录保留，但旧 `plan-N.approved.md` 不会自动成为 v2 的执行授权。

## 最短迁移路径

1. 在旧环境中结束正在运行的规划、执行和验收，核实相关作业/子进程已停止。保留原工作区及 `$DSH_HOME/plans` 历史，不把用户状态、凭据或计划目录提交到仓库。
2. 按现有部署方式更新插件并加载匹配的客户端构建；没有声明 `engines.dsh` 不等于支持所有内核。宿主必须有官方权限流程及结构化前台 `bash` 后端。依赖已安装的源码环境可在仓库根目录运行 `npm test` 构建并验证，不需要安装真实模型适配器来跑 fixtures。
3. 操作者从官方来源安装、审计并固定所选规划者与不同家族验收者的 ACP 适配器及依赖，在各自 CLI 登录。插件不再用 `npx` 自动下载。支持要求和官方参考见 [ADAPTERS.md](./ADAPTERS.md)。
4. 在原 DSH 会话调用 `dsh_x_plan_status`。旧批准显示需重新处理，不能凭旧文件继续执行。对旧活动任务用 `dsh_x_discard_plan` 明确放弃，然后用 `dsh_x_plan` 重新建立基线、预检和结构化计划；放弃不撤销现有改动。
5. 核对文件范围、阻塞问题和必需检查，调用 `dsh_x_approve_plan` 并确认新的原生审批卡。当前 DSH 会话执行后，用 `dsh_x_review` 单独批准运行检查，再由不同家族验收。

若存在锁或执行仍不确定，先处理下文的“中断与锁”，不要为了迁移删除状态文件、批准文件或锁，也不要另开一轮绕过未完成任务。

## 与旧版的主要区别

| 旧行为/假设 | v2 做法 |
|---|---|
| 四个主要工具 | 七个：新增 `dsh_x_revise_plan`、`dsh_x_plan_status`、`dsh_x_recover_plan` |
| 执行者固定描述为 DeepSeek | 执行者是当前 DSH 会话，不固定模型品牌 |
| 找不到适配器时回退 `npx` | 只解析已安装程序；缺失时停止，操作者安装与审计 |
| Claude 默认交给 Grok 验收 | 默认 codex → claude，claude → codex，grok → codex；也可显式指定不同家族 |
| 生成后再发现验收者不可用 | 两个适配器均先预检，记录路径、名称、版本并核对必需模式 |
| 自由文本加 `dsh-x-acceptance` | 唯一 `dsh-x-plan` JSON 契约，明确目标、文件、步骤、问题、检查 |
| 单个 `plan-N.approved.md` | `plan-N.approved-R.md/.json`，批准绑定修订、哈希、基线与适配器身份 |
| 看 `git diff HEAD` | 对照规划时基线，区分原有改动，包含任务期间已提交的变化 |
| 只读模型意味着检查也只读 | 模型审查只读；检查命令可能写文件，单独审批并走官方工具权限链 |
| 失败后一直修复 | 同一批准修订两次 `fail` 或一次 `inconclusive` 后停在 `needs_user` |
| 取消、重启后直接继续 | 检查状态和作业，必要时恢复普通死锁，再重新批准；不自动继续 |

### 改写计划格式

把旧的验收命令列表迁入 `checks`，每项有唯一 `id`、单行 `command` 和 `required: true`。把允许修改的文件逐个列入 `files`，使用仓库根目录相对路径，不能用目录或通配符代替。完整示例见 [README 的结构化计划](./README.md#结构化计划)。

一个尚未确定行为的计划可以保留：

```json
{
  "text": "空输入应返回空结果还是报错？",
  "blocking": true
}
```

它是 `questions` 数组中的一项，不是另一份计划契约。先取得答案并修订，再申请批准。没有可验证的检查时保持草稿，不用无意义的成功命令满足必填项。

每次 `dsh_x_revise_plan` 建立新轮次并保留旧草稿。批准前手动编辑草稿也必须经过新审批捕获；待审批期间任何正文、元数据或工作区变化会使请求失效。不要编辑批准副本来扩大范围。

## 推荐操作顺序

- 新任务：`dsh_x_plan` → 查看/澄清 → 必要时 `dsh_x_revise_plan` → `dsh_x_approve_plan` → 当前会话执行 → `dsh_x_review`。
- 一次 `fail`：阅读路径/检查 ID 对应的缺口，在原批准范围内修复，再验收。
- 两次 `fail`、`inconclusive` 或中断：`dsh_x_plan_status` → 检查现有改动和停止原因 → 用户决定 → 原任务仍适用时 `dsh_x_approve_plan`；重新批准保留原基线，生成新的不可变修订。
- 目标、范围或适配器已改变：先明确 `dsh_x_discard_plan`，再新建计划并批准。旧改动会留在工作区，成为新任务基线的一部分；应先审阅，不能把重新规划当作撤销或验收通过。
- 不继续：`dsh_x_discard_plan` 经确认关闭任务。它不还原代码、不终止外部进程，也不等于取消仍在运行的命令。

通用 `bash` 每次需要额外的命令级审批，且可能修改批准文件范围外的内容。`write` / `edit` 的精确路径和无符号链接检查不适用于约束 shell 内部行为。规划批准不覆盖任意命令、外部副作用或其他宿主权限。

## 中断与锁

先用 `dsh_x_plan_status` 查看任务与最近证据，并核实宿主作业管理器中的相关作业。取消请求或进程拥有者退出不一定意味着子进程都停止。

- 正常运行中的 `.task.lock`：等待或通过宿主正常停止操作，不强行接管。
- 同机、非 `retained` 且可证明原进程已退出的任务锁：用 `dsh_x_recover_plan` 申请官方审批。工具只释放匹配的普通死锁，不终止进程、不撤销文件。释放后检查工作区并重新批准。
- `retained` 锁：ACP 清理、shell 或验收作业停止状态不明确时会保留。即使原拥有者已退出，恢复工具仍拒绝释放；操作者需核实所有相关进程/作业停止，检查工作区、锁记录及宿主日志，再决定安全处理方式。
- 陈旧 `.store.lock`、损坏锁、异机锁或无法确认拥有者：没有自动恢复路径，需人工检查。普通恢复工具不会顺带删除存储锁。

不要盲删任何锁、改写状态为 `approved`、复制审批哈希或反复新建任务绕过门禁。状态或批准快照损坏也需要调查，不能把重新加载客户端视为修复。

## 新限制如何处理

- 初始工作区可以有脏文件。原有排除文件若不变化，可只保留不透明元数据，不把正文作为证据保存或发送；其新增、修改或删除会令证据不完整。不要为让验收通过而擅自删除这些文件。
- 文本快照有大小和路径数量上限；二进制、私密路径、疑似凭据、不可读取路径或截断输出不能支持自动通过。缩小任务或改用适合的人工验收，不能让模型忽略缺失证据。
- 子模块、`assume-unchanged` / `skip-worktree` 隐藏路径不支持完整证据捕获。不要绕过这些检查声称已覆盖整个仓库。
- 适配器的 `read-only` / `plan` 是协议要求，不是操作系统沙箱；Grok 仅有 `plan` 不符合本插件要求。版本预检也不是二进制、SDK 或来源安全认证。
- 凭据检测只是启发式；计划、代码片段及验收证据可能发给外部模型。不要使用真实凭据做测试，不依赖筛查来保证脱敏。
- 界面新增中文/英文状态、范围、检查结果和下一步提示，跟随宿主语言。原始计划、命令、路径与证据不会被翻译；旧历史显示不代表获得新执行授权。

仓库测试只使用本地 fixtures 和固定版本的官方运行时，不调用真实厂商模型。通过 fixtures 不能宣称任一 Codex、Claude 或 Grok 生产版本已获验证。升级前后的实际测试结果应以当次运行输出为准。
